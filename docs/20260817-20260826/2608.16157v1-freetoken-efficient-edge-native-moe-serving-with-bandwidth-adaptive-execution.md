## 摘要
前沿开放权重模型越来越普及，但服务这些模型在很大程度上仍假设数据中心基础设施。我们提出FreeToken，一个边缘原生的MoE服务系统，它不将个人机器视为小型GPU，而是视为一个统一、弹性的推理平台。FreeToken围绕本地AI的两个现实协同设计整个服务栈，包括模型布局与加载、专家驻留、CPU-GPU执行、代理状态重用以及运行时内存管理：代理工作负载不断改变其执行模式，边缘硬件暴露异构资源，其平衡因机器而异。FreeToken不是采用固定的卸载策略，而是将计算和模型状态持续映射到实际可用的资源上。FreeToken支持20多个MoE模型以及真实编码和使用工具的代理，硬件范围从8GB笔记本电脑GPU到单个工作站GPU。更重要的是，它改变了这些机器实际可服务的内容，从笔记本电脑上的35B模型，到游戏台式机上的284B模型，再到单个工作站GPU上的753B GLM-5.2。FreeToken将开放权重转化为可部署的本地软件，使用户已有的机器成为前沿规模智能的实用平台。我们在flashml.ai发布该系统。

## Abstract
Frontier open-weight models are increasingly available, but serving them still largely assumes datacenter infrastructure. We present FreeToken, an edge-native MoE serving system that treats a personal machine not as a small GPU, but as a unified, elastic inference platform. FreeToken co-designs the full serving stack, including model layout and loading, expert residency, CPU--GPU execution, agentic state reuse, and runtime memory management, around two realities of local AI: agent workloads continuously change their execution pattern, and edge hardware exposes heterogeneous resources whose balance differs from machine to machine. Rather than committing to a fixed offloading strategy, FreeToken continuously maps computation and model state onto the resources actually available. FreeToken supports more than 20 MoE models and real coding and tool-using agents across hardware ranging from an 8GB laptop GPU to a single workstation GPU. More importantly, it changes what these machines can practically serve, from a 35B model on a laptop to a 284B model on a gaming desktop and the 753B GLM-5.2 on a single workstation GPU. FreeToken turns open weights into deployable local software, making the machines users already own a practical platform for frontier-scale intelligence. We release the system at flashml.ai.

# FreeToken 论文总结

## 1. 核心问题与整体含义（研究动机和背景）

- **研究背景**：前沿开源 MoE 模型（如 Kimi-K3、GLM-5.2、DeepSeek-V4-Flash）的能力正快速逼近闭源系统，但其部署仍依赖昂贵的数据中心级 GPU 集群，导致“能获取模型”不等于“能负担运行”。大量消费级 GPU（如游戏本、工作站）虽然算力可观且闲置，却缺少能把异构 CPU/GPU/内存/互连资源统一组织起来的本地推理系统。
- **核心问题**：如何在个人边缘设备上高效服务“超过单卡显存”的前沿 MoE 模型，特别是面对 **agentic 工作负载**（上下文频繁编辑、多轮工具调用）和**异构、动态变化的边缘硬件资源**（显存、PCIe、内存带宽不稳定）时，现有的固定卸载策略（如 llama.cpp、KTransformers）性能严重退化。
- **整体含义**：FreeToken 将个人机器视为“统一的可弹性调度推理平台”，通过协同设计模型布局、专家驻留、CPU-GPU 执行、状态复用和内存管理，把开放权重转化为可实际部署的本地软件，使 35B–753B 级别的模型能在 8GB 笔记本 GPU 到工作站 GPU 上交互式运行，从而弥合“模型可获取性”与“模型可服务性”之间的鸿沟。

## 2. 方法论

### 2.1 核心思想

- **两大现实驱动**：① agent 工作负载的执行模式不断变化；② 边缘硬件资源异构，且 CPU/GPU/PCIe/内存带宽配比因机器而异。因此不采用固定卸载策略，而是持续将计算与模型状态映射到实际可用资源上。
- **三层协同设计**：
  1. **带宽自适应执行（Bandwidth-Adaptive Execution）**：把有限的边缘带宽当作运行时调度信号，而非常量瓶颈；
  2. **语义感知缓存（Semantic-Aware Caching）**：决定稀缺 GPU 内存中保留什么（专家、状态）；
  3. **弹性资源管理（Elastic Edge Resource Management）**：随运行环境动态调整 GPU 内存分配。

### 2.2 关键技术细节

- **两级专家内存层次**：CPU 端驻留完整专家池（source of truth），非专家权重常驻 GPU；GPU 剩余显存构成统一的可弹性 LRU 专家缓存，缓存槽以“（层，专家）”逻辑标识，而非张量分片。
- **Prefill 阶段**：
  - **全层双缓冲（Full-layer Double Buffering）**：为每一层准备两个完整专家层缓冲区；GPU 计算第 l 层时，专用传输流同时将第 l+1 层全部专家载入另一缓冲区，从而把专家传输完全隐藏在计算之后，避免 prefill 因激活大量专家而退化为“密集”传输。
  - **语义锚点状态缓存**：针对混合注意力/循环层（如 gated DeltaNet），在特殊 token 边界（如 `<think>`、工具调用、输出块等）保存 recurrent-state checkpoint；当 agent 框架删除/修改上下文块时，可从最近的存活锚点恢复，仅重新预填充新增后缀，避免全部重算。
- **Decode 阶段**：
  - **语义感知专家缓存**：利用路由的短时时间局部性（相邻 token 常命中相同专家），使用跨所有 MoE 层的共享 LRU 缓存，让 GPU 缓存持续跟随当前工作集，而非固定静态放置。
  - **q\* 带宽自适应策略**：对每个解码步中的 m 个未命中专家 M，划分为“PCIe 缓存填充集合 F”与“CPU 原位执行集合 C”，二者并发执行；划分比例由实测的两个带宽决定（见下文公式）。
- **CUDA Graph 兼容实现**：
  - 所有路由依赖的控制逻辑（去重、命中判断、q 计算、受害者选择）全部在 GPU 端以“数据”形式放在静态捕获图内，避免每层主机同步；
  - 使用单遍 kernel 找出 K 个最久未使用槽位；CPU 分支也捕获到同一 graph 中，通过持久化 task descriptor 和 pinned buffer 实现异构路径的无 Python 调度执行。
- **弹性内存生命周期**：
  - 可在调度安全点动态重建 GPU 专家缓存（调整缓存大小、KV-Expert 比例），无需重启引擎或重载主机专家池；
  - 快速启动：权重从磁盘读取时直接落入最终主机布局，之后才 pin 内存（避免为覆盖而零填充页面）；无需 GPU 预热，首个请求以冷缓存启动并正常“加热”。

### 2.3 核心公式（文字说明）

- 设 S 为单个专家大小，m 为未命中专家数，q 为填充数。
- 定义为 `M = F ∪ C`，`q = |F|`。
- PCIe 传输分支时延：`T_fill(q) ≈ qS / B_P`
- CPU 执行分支时延：`T_cpu(m−q) ≈ (m−q)S / (B_H − B_P)`（因为饱和 PCIe 传输后，CPU 只能利用残差带宽 `B_R = max(B_H − B_P, 0)`）
- 平衡两个并发分支可得最优值：`q⋆ ≈ m * B_P / B_H`。
- 其中 `B_P` 为实测 host→device 专家传输带宽，`B_H` 为实测 CPU 端专家处理带宽。该公式统一了“纯 PCIe 填充”“纯 CPU 执行”和二者混合三种情况，且无需算法近似，GPU/CPU 偏导数结果精确合并。

## 6. 主要结论与发现

- **性能大幅领先**：在 RTX 5090 上，FreeToken 在 Qwen3.6 上达到 77–83 tok/s（为最强基线的 1.8–2.3×），在 DeepSeek-V4-Flash 上达到 22–25 tok/s（1.5–1.9×）。
- **对 agentic 负载更稳定**：随任务从单轮数学到复杂编码/工具调用，FreeToken 解码速率保持在单轮水平的 12% 以内，而 KTransformers 在 W2 时已损失 31% 性能。
- **尾延迟显著改善**：FreeToken 在所有负载下最差 TTFT 均小于 44s；各基线至少在某场景超过 150s（KTransformers 高达 946s），可触发实际 agent 客户端超时。
- **跨硬件普适性**：在 5 个消费级系统上比最强基线提升

跨硬件普适性：在 5 个消费级系统上比最强基线提升 1.26–2.7×，且 RTX 4060 Laptop（8GB）上仍能以约 20 tok/s 服务 Qwen3.6-35B-A3B，证明“小显存设备也能跑前沿 MoE”并非空谈。
- **RTX PRO 6000 工作站演示**：在 96GB 显存上可直接承载 GLM-5.2（753B，NVFP4）的全部参数，FreeToken 仍能保持稳定解码，验证了其设计可平滑扩展至“整模型驻留单卡”的极限场景。
- **对 prefill 双缓冲的量化验证**：Full-layer double buffering 使 35B 模型 prefill 阶段速度提升约 3.4×（与不启用双缓冲相比），且整体 TTFT 降低，说明该机制有效消除了“专家预取暴露在关键路径”的问题。
- **LRU 语义缓存优于静态放置**：在相同路由轨迹下，FreeToken 的共享 LRU 专家缓存在各缓存容量上 miss 率均最低；当缓存容量较小时（如 40–60 槽），其 miss 率远低于 KTransformers 的 prefill-update 策略，说明局部性感知的替换策略比启发式静态放置更鲁棒。

## 7. 局限性

- **模型覆盖有限**：主实验仅验证了 2 个前沿 MoE（Qwen3.6-35B-A3B、DeepSeek-V4-Flash），GLM-5.2 仅作为单点演示；论文宣称支持 20+ MoE 架构，但未系统展示。
- **环境差异**：部分评测在租用服务器上通过 CPU 线程限制与 NUMA 绑定模拟边缘主机，与真实笔记本/桌面的功耗、散热、动态调频行为仍存在差异。
- **量化与精度敏感性**：主要采用 BF16/NVFP4/MXFP4 等格式，未深入分析更低比特量化（如 INT4/INT2）下的专家形态对缓存与带宽策略的影响。
- **agentic 场景多样性**：4 类工作负载虽具代表性，但未涵盖长时间 human-in-the-loop 交互、多用户并发、或流式工具输出等更多真实形态。
- **单机单进程假设**：FreeToken 针对单用户边缘部署设计，未涉及多实例共享 GPU、集群调度或安全隔离等云侧问题。

## 8. 核心贡献与意义

- **系统层面**：首个针对 agentic 工作负载与异构边缘硬件协同设计的 MoE 推理系统，提出“带宽自适应执行 + 语义感知缓存 + 弹性资源管理”三位一体方案，将以往固定卸载问题转化为在线调度问题。
- **算法层面**：给出无需近似、可用闭式解确定的 q* 划分公式，把“PCIe 传输 vs. CPU 原位计算”的并发权衡精确刻画为带宽比问题，具有较强可迁移性。
- **工程层面**：CUDA Graph 内实现全部路由决策与 CPU/GPU 异构并行，去除逐层主机同步，直接支撑了端到端低延迟；弹性缓存重建与快速启动提升了实际部署体验。
- **对领域的意义**：推动“前沿模型本地化”从“能否跑起来”转向“能否流畅服务真实任务”，为消费级 GPU 成为可信 AI 推理底座提供了可复现的系统范式。

## 9. 总结

FreeToken 的核心洞察是：边缘设备并非“显存不足的退化平台”，而是“带宽与算力配比可感知、可编排的动态平台”。通过将模型状态（专家）与执行路径按实时资源状态持续重映射，它在 8GB 笔记本 GPU 上实现了此前需多卡 A100 才能支撑的交互式 agent 工作负载。该工作对个人 AI 部署、隐私敏感场景和边缘计算具有直接实用价值，也为后续研究提供了“卸载决策即资源调度”的新视角。
