## 摘要
作为校园网中的一层，核心层或骨干网络应提供内部与外部网络（包括其他校园网或互联网）之间的互联和路由。基于这一需求，设计该层以实现高可用性的互联和流量路由是首要任务。通过使用软件定义网络（SDN）范式，我们尝试在校园网核心层设计中采用网络拓扑和路由协议的最佳实践，并以某大学校园网核心层为用例。我们使用RouteFlow作为SDN平台，在OpenFlow（OF）网络基础设施上支持传统路由协议，即开放最短路径优先（OSPF）。实验测试平台/环境由两台虚拟机（VM）组成。第一台虚拟机用作SDN/OF数据平面，使用Mininet网络仿真器中的Open vSwitch；第二台虚拟机代表SDN控制平面，包含RouteFlow和POX控制器。我们通过使用ping测试拓扑中OF交换机及连接到交换机的主机之间的互联性来评估设计。我们还使用tcpdump监控通过交换机所有网络接口的流量，以跟踪数据包的路由。该案例进行了评估，因为我们需要确保数据包通过SDN平台顶部的虚拟网络中实现的OSPF从源到目的地以最短路径路由。

## Abstract
As one of the layers in campus network, core layer or backbone network should provide interconnectivity and routing between internal and external networks, including other campus networks or the Internet. With that requirement, designing this layer to be highly available to interconnect and route traffic is a high priority. By using software-defined networking (SDN) paradigm, we attempt to design core layer in campus network employing best practices of network topology and routing protocol at the layer with a use case of core layer in a university campus network. We use RouteFlow as the SDN platform supporting a traditional routing protocol, i.e. Open Shortest Path First (OSPF), over OpenFlow (OF) network infrastructure. The experimental testbed/environment consists of two virtual machines (VMs). The first VM is used as the SDN/OF data plane with Open vSwitch in Mininet network emulator, and the second one representing SDN control plane comprising RouteFlow with POX controller. We evaluated the design by testing the interconnectivity using ping for the OF switches in the topology and hosts that are connected to the switches. We also tracked the route of the packets by monitoring traffic passed through all network interfaces of the switches using tcpdump. This case was evaluated since we need to make sure that packets were routed with the shortest path from source to destination using OSPF that was implemented in the virtual network at the top of the SDN platform.

## 1. 核心问题与研究动机

- 校园网核心层（core layer / backbone）承担着校园内部网络与外部网络（其他校园网或互联网）之间的互联与路由职责。
- 该层最关键的需求是**高可用性**，即必须稳定、可靠地完成跨网络的数据转发和路由选择。
- 传统网络设备中，控制平面和数据平面耦合在一起，网络管理、扩展和灵活性受到限制。
- **软件定义网络（SDN）**将控制平面与数据平面分离，使网络具备可编程性、集中控制性和灵活性。
- 本文针对真实校园网案例（印度尼西亚 Jenderal Soedirman 大学，Unsoed）的**核心层**，尝试用 SDN/OpenFlow 架构完成设计，并采用传统路由协议 OSPF 来实现动态路由。
- 使用 **RouteFlow** 作为 SDN 平台，在 OpenFlow 基础设施上运行传统 IP 路由协议，从而兼顾 SDN 的可编程性和传统网络协议的兼容性。

## 2. 提出方法论

### 2.1 设计思想

- 核心层采用 **三角形拓扑（triangle topology）**，而不是方形拓扑，因为三角形拓扑能够提供等价冗余路径，同时保证确定性收敛，符合 Cisco 关于高可用校园网的最佳实践。
- 拓扑中设备之间采用点对点链路，链路带宽设置为 1 Gbps。
- 路由协议选择 **OSPF**：
  - 开放、广泛使用、适用于自治系统内部（intra-AS）路由；
  - 属于链路状态协议，使用 Dijkstra 最短路径优先（SPF）算法；
  - 与 Unsoed 校园网核心层实际使用的路由协议一致。

### 2.2 SDN 与 RouteFlow 平台

- 使用 **OpenFlow** 作为 SDN southbound 通信协议。
- 使用 **RouteFlow** 作为 SDN 平台：
  - 包含 RFProxy、RFServer、RFClient 三个核心组件；
  - 通过虚拟网络复制物理/虚拟网络拓扑；
  - 在虚拟路由器上运行传统路由引擎（如 Quagga），从而支持 OSPF、RIP、IS-IS、BGP 等传统路由协议。
- 控制器选择 **POX**，原因：
  - POX 是 Mininet 和 RouteFlow 中常用的基础控制器；
  - 实验规模较小，POX 足以满足需求；
  - 便于快速实现原型验证。

### 2.3 实验环境与实现流程

- 实验使用两台虚拟机组成虚拟测试平台：
  - **RouteFlow VM**：运行 RouteFlow + POX 控制器，Ubuntu 12.04.5；
  - **Mininet VM**：运行 Mininet + Open vSwitch，模拟 SDN/OpenFlow 数据平面，Ubuntu 14.04.5；
  - 两台 VM 通过宿主机的 TUN 接口和虚拟网桥连接。
- 数据平面由 3 个 Open vSwitch 交换机（s1、s2、s3）组成三角形拓扑，并连接 3 台主机（h1、h2、h3）。
- 主机分别属于不同网络：
  - h1：172.31.1.100/24，连接 s1；
  - h2：172.31.2.100/24，连接 s2；
  - h3：172.31.3.100/24，连接 s3。
- OSPF 配置：
  - hello interval 1 秒，dead interval 4 秒；
  - 使用 backbone area；
  - 在 RouteFlow 中通过 LXC 虚拟路由器运行 Quagga。
- 验证方法：
  - **互连测试**：使用 ping 测试主机对之间的连通性；
  - **路由路径测试**：使用 tcpdump 捕获所有交换机接口上的流量，再使用 Wireshark 分析 ICMP 数据包实际转发的路径。

## 3. 实验设计

- 没有使用公开数据集，而是采用**真实校园网核心层场景**作为设计用例。
- 场景规模较小但具有代表性：3 台核心交换机、3 个独立网段、3 台测试主机。
- 所谓的“benchmark”是 OSPF 理论上的最短路径：
  - h1 → h2 应经过 s1 和 s2；
  - h2 → h3 应经过 s2 和 s3；
  - h3 → h1 应经过 s3 和 s1。
- 没有对比其他 SDN 控制器、其他路由协议或其他拓扑结构，主要验证“OSPF over RouteFlow/OpenFlow”是否可行。

- 但整体充分性有限，无法充分证明该设计在高负载、故障切换、规模扩展等真实生产环境中的可用性。

## 6. 主要结论与发现

- 基于 RouteFlow 的 SDN/OpenFlow 架构，可以在校园网核心层中顺利运行传统 OSPF 路由协议。
- 互连测试表明，所有交换机之间以及主机之间都能正常通信。
- 数据包路由跟踪结果显示，ICMP 数据包均按照 OSPF 计算的最短路径从源转发到目的地：
  - h1→h2 走 s1→s2；

- h2→h3 走 s2→s3；
- h3→h1 走 s3→s1；
- 实际路径与 OSPF 理论最短路径完全一致，证明 RouteFlow 能够正确地将 OSPF 计算出的路由映射为 OpenFlow 流表项，数据平面按预期转发。
- 验证了 SDN 架构下“集中控制 + 分布式转发”的可行性，同时保留了传统路由协议（OSPF）在动态路由和故障适应方面的优势。
- 作者认为该设计可作为 Unsoed 校园网核心层升级改造的参考方案，并且具备向更大规模网络扩展的潜力。

## 7. 局限性与未来工作

- **实验规模有限**：仅含 3 台交换机和 3 台主机，未能体现校园网核心层真实流量负载、多租户隔离、安全策略等复杂需求。
- **缺乏故障场景验证**：未测试链路中断、设备失效等情况下 OSPF 的重收敛行为，而高可用性恰恰是核心层的关键指标。
- **性能与可扩展性未评估**：未测量 RouteFlow/POX 控制器的流表安装延迟、每秒处理请求数、路由引擎同步开销等指标；POX 作为单线程控制器，在大型网络中可能成为瓶颈。
- **未比较其他 SDN 方案**：未与纯 OpenFlow 集中式路由（如 ONOS、Ryu+OSPF）、或传统物理路由器方案进行横向对比。
- **未涉及安全与网络管理**：无访问控制、ACL、QoS、流量监控等校园网常用功能的设计。
- **未来工作**：作者建议在更大规模拓扑中测试，引入链路故障和动态流量场景，评估控制器性能，并探索将 SDN 核心层与实际校园网生产环境集成的方案。
