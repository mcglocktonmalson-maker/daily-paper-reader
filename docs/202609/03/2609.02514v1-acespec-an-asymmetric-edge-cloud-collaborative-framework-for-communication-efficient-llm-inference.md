## 摘要
在边缘设备上部署大型语言模型（LLM）通常依赖于模型压缩或分割推理。然而，压缩会降低推理能力，而分割推理则饱受严重的广域网（WAN）通信瓶颈之苦。边缘-云端投机解码成为一种有前景的替代方案，利用边缘小模型生成令牌供云端验证。然而，在波动的WAN环境下，不可避免的预测拒绝会引发灾难性的流水线停滞和全网回滚，抵消协作增益。为解决此问题，我们提出AceSpec，一种非对称边缘-云端协作框架。AceSpec利用未饱和的边缘计算资源主动构建概率状态缓存，有效将全网流水线刷新转化为O(1)局部内存查找。为节省带宽，它采用非对称通信协议，上行传输最小主链索引，下行传输紧凑稀疏分布。此外，我们引入一种网络感知的、基于拉格朗日优化的资源分配策略，动态最大化局部缓存命中率。评估表明，AceSpec实现了最高3.52倍的吞吐量加速，并表现出卓越的带宽免疫力，即使在严重受限的50 Kbps WAN条件下也能维持接近峰值的推理性能。

## Abstract
Deploying Large Language Models (LLMs) on edge devices typically relies on model compression or split inference. However, compression degrades reasoning capabilities, while split inference suffers from severe Wide Area Network (WAN) communication bottlenecks. Edge-cloud speculative decoding emerges as a promising alternative, leveraging an edge small model to draft tokens for cloud verification. Yet, over volatile WANs, inevitable prediction rejections trigger catastrophic pipeline stalls and network-wide rollbacks, neutralizing collaborative gains. To overcome this, we propose AceSpec, an asymmetric edge-cloud collaborative framework. AceSpec utilizes un-saturated edge compute to proactively construct a probabilistic state cache, effectively transforming network-wide pipeline flushes into $\mathcal{O}(1)$ local memory lookups. To preserve bandwidth, it employs an asymmetric communication protocol that transmits minimal main-chain indices uplink and compact sparse distributions downlink. Furthermore, we introduce a network-aware, Lagrangian-optimized resource allocation strategy that dynamically maximizes the local cache hit rate. Evaluations demonstrate that AceSpec achieves up to a 3.52$\times$ throughput speedup and exhibits exceptional bandwidth immunity, sustaining near-peak inference performance even under severely constrained 50 Kbps WAN conditions.

  - 部分方案需要额外微调或辅助网络，通用性受限。

**核心问题：** 如何在易变、低带宽的 WAN 条件下实现高效、通用、无需训练的边云协同 LLM 推理，避免预测拒绝导致的回滚惩罚？

## 2. 方法论：AceSpec 框架

**核心思想：** 利用边缘设备丰富的并行计算资源（而非闲置等待网络），主动构建**概率多分支 token 树缓存**，将高成本的网络级流水线冲刷转化为 O(1) 本地内存查找；同时采用非对称通信协议最小化上下行数据量。

### 2.1 系统架构与执行流程

系统包含两个实体：

- **边缘客户端（Edge Client）**：运行轻量级小语言模型（SLM），维护三个子系统——树形草稿器（Tree-based Drafter）、概率 KV 缓存管理器（Probabilistic KV Cache Manager）、本地重采样器（Local Resampler）。
- **云服务器（Cloud Server）**：运行高参数目标 LLM，执行高度并行的验证循环；云只作为"评估者"，不控制最终 token 选择。

工作流：

1. 边缘 SLM 生成主链草稿序列（长度 γ），只将**主链 token 索引**经上行链路发送到云（将上行通信量降为标量数组，节省上行带宽）；
2. 边缘在等待云端验证期间（T_cloud），利用空闲计算资源执行**异步多分支扩展**，从主链各潜在拒绝位置出发生成替代分支；
3. 云端对主链进行单次前向并行验证。若某位置 token 被拒绝，云端不进行重采样，而是将拒绝位置索引与对应的**部分目标概率分布**打包返回；
4. 边缘根据返回信息执行本地重采样确定正确 token，再以该 token 为查询键在概率缓存中检索，命中则通过 COMPACT_KV 操作 O(1) 恢复状态，跳到下一轮流水线周期。

### 2.2 关键技术细节

**（1）非对称通信协议：**
- 上行：只传主链 token 的标量索引序列；
- 下行：仅在拒绝时传回稀疏化的部分目标概率分布。

**（2）树注意力掩码（Tree Attention Mask）：** 为避免分支数量 N 带来的线性草稿延迟，AceSpec 通过专用掩码在一次前向传播中并行生成所有分支。掩码包含三个子块：
- **共享前缀块（Shared Prefix Block）**：允许全部分支访问已验证的历史上下文；
- **主路径分支块（Main-Path Branch Block）**：将从深度 s_j 出发的分支限制为只关注主草稿的前 s_j 个 token；
- **后缀对角块（Suffix Diagonal Block）**：施加对角隔离约束，使每个推测 token 只关注自己的祖先序列。

**（3）非对称解码循环（Algorithm 1）：** 边缘在收到验证反馈 (π, P̂_target) 后，先本地重采样出修正 token x_resampled，用 (π, x_resampled) 作为查询键查找本地树缓存 T。命中即 O(1) 状态恢复；未命中才执行回滚与顺序重草稿。

### 2.3 数学公式与优化

**回滚惩罚模型（揭示现有方法瓶颈）：**

- 单链全序列接受概率：p_single_hit = α^γ（随长度指数衰减）；
- 期望惩罚时间：**E[Penalty] = (1 − α^γ) × (RTT + T_redraft(γ))**；
- 流水线实际吞吐：**R_pipe = E[L] / (T_ideal + E[Penalty])**；
- 当 α 低时惩罚系数趋近于 1，流水线气泡主导，回到同步基线。

**AceSpec 的加速比下界：**

**S ≥ S_ideal / (1 + (1 − P_tree_hit(T)) · ρ)**

其中 S_ideal 为理想加速上限，ρ = T_bubble / T_ideal 为回滚惩罚比。

**两级约束优化框架：**

- **网络感知的预算约束（Network-Aware Budgeting）：** 本地树构建时间必须隐藏在云周转时间内（T_tree_draft(B) ≤ RTT(t) + T_verify），即

  **B*(t) = min(B_max, ⌊T_tree_draft⁻¹(RTT(t) + T_verify)⌋)**

- **任务感知的拓扑分配（Task-Aware Shape Allocation）：** 给定预算 B*(t)，求解最优分支分配向量 F = [F₀, F₁, …, F_{γ−1}]，最大化树命中率：

  **max Σ log(α + (1 − α)R(F_k))**

  约束为 ΣF_k ≤ B_alloc(t)。权重引入前缀生存概率 α^k 后进行拉格朗日求解，结合 LLM 词表分布的长尾/幂律特性 R(F_k) ≈ 1 − cF_k^{−β}，得到闭式解：

  **F*_k = B_alloc(t) · ((1 − η)/(1 − η^γ)) · η^k**

  其中衰减因子 η = α^{1/(β+1)} ∈ (0,1)。该策略揭示了关键洞见：**资源应按几何衰减分配**——浅层（早期 token）最易被拒绝时命中概率最高，因此分配更多分支；随深度增加，达到该深度的概率指数衰减，故分配显著递减，实现计算冗余的最大化利用。

## 6. 主要结论与发现

1. **AceSpec 在绝大多数配置下取得最优或接近最优的吞吐加速比**，最高达到 **3.52×**（LLaMA-1B/70B + HumanEval）；

4. **非均匀几何衰减分配策略优于均匀分配和单链基线**：Non-Uniform Branch 在 GSM8K 上达到 24.37 tokens/s vs 单链 20.14、均匀 21.58，同时命中率最高达 0.97（GSM8K/HumanEval）；
5. 敏感性分析表明：
   - 预算 B 存在**边际收益递减**特性（20→40 提升快，80 后趋于平台），提示实际部署中需权衡算力与命中率；
   - 即使采样温度升至 1.7（高随机性），AceSpec 命中率仍保持 81% 以上，表明其同时适用于确定性推理和创意生成任务；
6. 论文证实了理论建模与工程实践的一致性：**只有在本地树构建时间小于云端验证周转时间时，AceSpec 才能充分发挥优势**。

2. **数据集规模与多样性有限**：仅使用三个数据集（GSM8K/HumanEval/Alpaca），且未报道各数据集具体样本量、评估指标细节（如 pass@k 在 HumanEval 上是否适用等）；
3. **带宽鲁棒性实验中带宽数值跨度分布不均匀**：100→0.1 Mbps 之间以较大幅度递减（缺少 10 Mbps 以下的多个中间值），对从 0.1 Mbps 到 50 Kbps 区间的行为刻画主要依赖少量数据点，可能遗漏临界变化；
4. **边缘类型单一**：仅在 Jeston AGX Orin 一种边缘硬件上进行了测试，未考虑手机端、树莓派等更弱算力设备或不同边缘硬件之间算力差异的影响；
5. **对比方法有限**：与最前沿的论文引用列表相比，实际实验对比仅选了 PicoSpec 和 DSSD 两个较新的分布式投机解码方案。PipeSD、E2-SCI 等论文中重点讨论的框架并没有在实验中参与对比（虽然表格中列出的对比方法中未出现它们），可能影响定位的完整性——这也可能是因为论文发表时间较早。

**方法/性能层面：**

1. **存在明显退化场景**：在 Qwen-1.7B/32B + HumanEval 配置下仅为 0.98×，比自回归基线还低，说明它在某些草稿模型较重、任务语法约束强时无法发挥优势，论文也承认了这一点；
2. **计算/通信的平衡依赖于 RTT 探测的实时准确性**：实际中 RTT 波动剧烈时预算 B*(t) 的计算可能滞后或过估计，论文仅在带宽维度上进行了静态测试，未对动态变化的 RTT 做压力测试；
3. **对树形缓存大小的内存开销与 KV 缓存管理开销分析不足**：多分支树需存储大量 KV 状态与概率缓存，文中虽然提到 Compact_KV，但没有给出内存占用对比数据或在大上下文

...或在大上下文长度场景下的实际内存增长曲线，因此难以评估长序列生成（如数万 token 的对话、文档摘要）时树缓存与 KV 缓存是否会成为新的瓶颈。

4. **缺少动态网络与真实并发压力的测试**：实际 WAN 中的 RTT 存在波动、突发拥塞和排队延迟，论文仅在稳态延迟/带宽梯度下测试，未对 RTT 抖动、丢包、重传等场景进行验证；也未模拟多个边缘客户端同时访问云服务器的竞争情况。
5. **对模型安全性、隐私与公平性未作讨论**：AceSpec 需要将用户上下文 token 上传到云服务器参与验证，在敏感场景下存在数据暴露风险；边缘侧概率缓存和本地重采样可能改变输出分布，论文未分析对生成内容质量、安全对齐的影响。

## 9. 总体定位与未来方向

总体而言，AceSpec 是为解决 WAN 环境下边云协同 LLM 推理的“通信墙”而提出的原创性系统设计。其核心贡献在于将边缘设备的并行算力从“等待”转变为“主动预测缓存”，用概率多分支树规避了传统投机解码中拒绝回滚的全网同步代价，并通过非对称通信协议将数据传输量压缩至接近理论上限。实验证明其在 50 Kbps 极低带宽下仍能保持吞吐，优于现有同步与异步流水线方案，且无需微调、即插即用，具有较强的实用潜力。

但在走向真实部署前仍需解决几个关键问题：一是树形缓存的内存开销在大上下文下的可扩展性；二是对动态网络状况（RTT 抖动、丢包）的鲁棒性；三是需要提供更全面的延迟、能耗与成本对比，证明其在真实边缘设备上的收益。未来可将 AceSpec 与动态带宽感知策略、压缩 KV 缓存、多级模型分层结合，并扩展到移动端 NPU 或更异构的边缘集群，以进一步释放其潜力。
