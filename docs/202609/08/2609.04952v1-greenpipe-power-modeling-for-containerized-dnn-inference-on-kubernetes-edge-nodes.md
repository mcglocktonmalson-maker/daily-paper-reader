## 摘要
分布式DNN推理日益部署在容器化的边缘-云环境中，工作负载在设备上运行或通过网络暴露给远程客户端。在缺乏如RAPL等硬件功耗计数器的资源受限ARM节点上进行准确的在线功耗估计仍是一个挑战，而仅依赖CPU的模型无法捕获多资源行为。我们提出了GreenPipe，一种自动化的配置-训练-验证流水线，可根据外部功率计的测量构建多资源回归模型，并按比例将功耗归因于容器。GreenPipe在K3s边缘-云测试平台上的树莓派4边缘节点上进行了评估，涵盖了使用三种视觉模型、多种精度、线程数以及本地和服务场景的DNN推理。系统级MAPE为6.3-9.4%，平均比仅CPU压力和仅利用率基线改善26.9%的MAPE。我们联合报告了推理延迟和每次推理的能量，揭示了不同工作负载配置下的性能-能量权衡。

## Abstract
Distributed DNN inference is increasingly deployed in containerized edge-cloud environments, where workloads run on-device or are exposed to remote clients over the network. Accurate online power estimation on resource-constrained ARM nodes without hardware power counters such as RAPL remains a challenge, and CPU-only models fail to capture multi-resource behavior. We present GreenPipe, an automated profiling-training-validation pipeline that builds multi-resource regression models from external power meter measurements and attributes power to containers proportionally. GreenPipe is evaluated on a Raspberry Pi 4 edge node in a K3s edge-cloud testbed, covering DNN inference with three vision models, multiple precisions, thread counts, and both local and serving scenarios. System-level MAPE is 6.3-9.4%, improving over CPU-stress and utilization-only baselines by 26.9% MAPE on average. We jointly report inference latency and energy per inference, exposing performance-energy trade-offs across workload configurations.

  - 如何在缺乏硬件功耗接口的 ARM 边缘节点上，对容器化 DNN 推理实现准确、在线的**节点级与容器级功耗估计**？

  - **容器层面的挑战**：Kubernetes 提供了 cgroup 隔离与指标，但节点级功率计无法识别每个容器的功耗贡献；本地推理与网络服务推理压制的资源路径不同，单一模型难以兼顾。

- **整体含义与意义**：
  - 该研究填补了"ARM 边缘节点 + Kubernetes 容器化 + DNN 推理在线功耗建模"的空白。GreenPipe 不依赖专用硬件，通过数据驱动方法可以在实际集群中实现较为精确的功耗估计，为边缘侧的能耗监控、容器调度、绿色计算提供基础工具。

### 2. 论文提出的方法论

#### (1) 核心思想
GreenPipe 采用 **数据驱动的功耗建模** + **启发式容器功耗归属**。其核心逻辑是：通过外部功率计获取节点级真实功率作为标签，同时采集 CPU、缓存、内存、磁盘、网络等多维度资源指标作为特征，训练回归模型，在线运行时以指标预测功率，再按容器资源占用比例将节点功耗分解到各容器。

#### (2) 系统架构与两阶段流程

| 阶段 | 内容 |
|---|---|
| 离线工作流（Offline Workflow） | 在边缘节点以 Kubernetes Job 方式启动容器化训练基准程序；资源监视器（DaemonSet）与 Prometheus（StatefulSet）采集时间序列数据；外部功率计以 1Hz 频率记录真实功耗。数据传到服务器后进行对齐预处理、特征选择与训练验证。 |
| 在线运行阶段（Online Operation） | 选定模型存入集群可访问卷（NFS）中；DaemonSet 增加 estimator sidecar，以秒级频率加载模型从实时指标预测节点功耗；再按比例归属到容器；预测结果输出到 Prometheus。 |

#### (3) 资源监控设计
- 基于 Kepler 框架定制改造，重写并针对 ARM 架构重新构建镜像（原版 Kepler 仅依赖 RAPL，不适用树莓派）。
- 监控指标覆盖：CPU 行为（PMU 周期/指令、eBPF cpu_time）、缓存行为（cache_miss、page_cache_hit）、内存、网络（eBPF 中断与 /proc/net/dev 带宽）、磁盘（block I/O 中断与 cgroup io.stat）等。

#### (4) 训练基准（Training Benchmarks）
分为三类，全部容器化执行：

1. **微基准（Micro-benchmarks）**：使用 stress-ng（cpu_int8/fp16/fp32/matrixprod、vm-rw、hdd）与 iperf（网络）。
2. **组合基准（Combined）**：CPU+内存+磁盘（模拟本地推理场景）、全组件同时压制（模拟网络服务推理）。
3. **DNN 目标基准**：DeepBench 的低层 DNN 算子（gemm 稠密/稀疏矩阵乘、卷积计算），用于捕获 DNN 推理行为而无需依赖深度学习框架。

#### (5) 数据处理与特征选择
- 将资源指标与功率计数据按 1Hz 时间戳对齐，剔除缺失值，特征归一化。
- 通过 Pearson 相关分析选出 **7 个代表特征**：cpu_cycles、cpu_time、cpu_instructions、cache_miss、page_cache_hit、net_bandwidth、disk_io。
- 最终训练数据集：12 个 benchmark 共 13938 个样本。

#### (6) 模型训练与选择
- 将功耗估计视为监督回归任务，对比了 11 种 scikit-learn 模型：LR、Lasso、Ridge、SGD、PR（多项式回归）、DT、RF、GB、XGB、KNN、SVR。
- 根据验证集的 MAPE 选择最终模型——本实验选择了 LR（线性回归）用于在线部署。

#### (7) 容器级功耗归属的核心公式

**动态功耗分解公式**：
```
P_dyn(node) = P(node) - P_idle(node)
```
其中 P_idle(node) 为系统空闲时观测到的稳态最小功率。

**容器动态功耗按比例归属公式**：
```
P_dyn(container) = (R_container / R_node) · P_dyn(node)
```
R 为加权资源总和：R = Σ wᵢ·Rᵢ，权重 wᵢ 从训练的 LR 模型系数获得，且保证 Σ R_container = R_node。

**容器静态功耗按进程数归属公式**：
```
P_idle(container) = (N_proc,container / N_proc,node) · P_idle(node)
```

**最终容器功耗**：
```
P(container) = P_dyn(container) + P_idle(container)
```

> 作者明确指出该归属方法是**启发式**，适用于运行可视性；由于外部功率计仅提供节点级真值，未宣称容器级精确度得到验证。

### 6. 主要结论与发现

1. **GreenPipe 系统级功耗预测精度良好**：在验证推理负载上系统级 MAPE 为 **6.3%–9.4%**，所有 GreenPipe 候选模型的 MAE 在 0.22–0.49 W 之间，均优于两个 CPU-centric 基线。
2. **训练基准的广度比回归器选择更关键**：GreenPipe 相对于 CPU-stress 训练基线平均降低 MAE 46.9%、MAPE 26.9%；相比之下，11 种回归器之间差异不大，说明物理基准覆盖多资源行为比模型选择更影响精度。
3. **CPU-only 模型有明显局限**：仅用 CPU 利用率的简单线性基线（Baseline LR）在 DNN 推理负载上误差明显偏大（MAPE 远高于 GreenPipe），证明缓存、内存、网络、磁盘等指标对功率预测的重要性。
4. **不同工作负载因素的影响不同**：
   - 模型架构与精度对预测误差影响有限——MobileNet 误差略高于大模型；整数推理（int8）误差略高于浮点。
   - **线程数、推理引擎与部署模式（本地 vs 网络服务）是主导预测难度的因素**。
   - 随着线程数增加，误差逐步增大；但即便 4 线程时，多数模型 MAPE 仍在约 10% 以内。
   - pb（TensorFlow Serving）负载的预测精度优于 tflite（LiteRT）负载。tflite 耗电量被系统性低估，可能是 LiteRT 在边缘设备上更优的优化所致。
5. **延迟-能耗权衡呈现模型非线性特征**：
   - ResNet 延迟与能耗最高；int8 精度在延迟和能耗上均最优。
   - **线程效应对模型大小有依赖**：小模型从并行中获得延迟与能量的双重收益；大模型在高线程数下功耗上升抵消了运行时间缩短，能耗不降反升。
   - 部署模式与线程数对延迟-能量前沿的影响大于模型家族/精度的作用——能效感知的调度应优先考虑并行度与部署模式。
6. **在线估计与容器归属开销很低**：监视器+估算器占节点功耗 <2%。

### 8. 不足与局限

#### (1) 硬件覆盖度有限
- 仅在单个 Raspberry Pi 4（ARM Cortex-A72）上验证。不同 ARM SoC（如 Apple Silicon、Ampere）、x86 设备或有 GPU 的边缘平台（NVIDIA Jetson 系列）上，模型的迁移性与准确性未得到验证。
- 树莓派 CPU 频率政策（ondemand governor）、供电方式（USB 供电）等都可能引入特定硬件偏差。

#### (2) 容器级功耗归属缺乏真值验证
- 外部功率计只能提供节点级能耗标签，论文中的容器级归属（按动态资源占比与进程数分配）**无法用地面真值验证**。
- 分配方式依赖 LR 模型的系数作为加权权重，其物理合理性依赖线性模型假设的成立性，在部分负载下可能不准确。

#### (3) 在线估计的误差范围与实际动态场景仍有关
- 在线阶段每秒级预测，而功率计采样 1Hz——单位时间窗口内负载突变可能造成较大瞬时误差。
- 作者也在未来工作中指出，在线部署无法获取同步真实功耗标签，需要在获得新数据时进行周期性仪表辅助再校准（meter-assisted recalibration）。

#### (4) 资源与功耗采集基础设施较复杂
- 实现高度依赖 eBPF 内核事件、PMU 计数器及定制内核。普通用户需要在边缘设备上重新编译内核并配置专门的 ebpf 子系统，部署门槛较高。
- 论文未提供在非 Linux 边缘环境（如 FreeBSD 或 Windows IoT）或受限容器环境（如无特权 Pod，无法加载 eBPF）中的可行性分析。

#### (5) 精确度报告的深度不足
- 没有按不同精度（int8/fp16/fp32）× 不同场景（local/serving）细化每个具体工作负载的误差区间，部分结论仅给出"avg"列。
- 没有与其他容器级功耗工具（如 Kepler、PowerAPI/SmartWatts，在支持它们的硬件上）做直接的量化对比——只在树莓派上对比了两种 CPU-centric 基线。

#### (6) 推理/请求负载的多样性较弱
- DNN 任务只选择了"图像分类"这一类应用与三个 CNN 模型，缺少 NLP/Transfomer/目标检测/语音模型等当前边缘部署的主要负载，因此结论对更广泛的 DNN 推理工况是否成立尚不确定。
